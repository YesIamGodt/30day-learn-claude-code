# Day 15: 里程碑：你的 AI 已经能跑了！

## 这一节要解决什么问题？

经过 14 天的学习，我们已经掌握了构建一个 AI Agent 的所有核心模块。这些模块目前是分散的，现在终于要把它们拼在一起了。

想象一下搭积木：你有一堆积木块——轮子（工具系统）、大脑（AI 调用）、记忆（历史管理）、眼睛（上下文窗口监控）、安全门（权限守卫）——现在要把它们组装成一辆能跑的车。

## 为什么这个架构能工作？

每个模块各司其职，通过接口通信：

- **REPL** 只负责接收用户输入和展示输出，不管业务逻辑
- **命令系统** 只做路由，特殊命令本地处理，普通消息传给 QueryEngine
- **QueryEngine** 是核心引擎，驱动整个 ReAct 循环，不知道也不需要知道谁在调用它
- **权限守卫** 在工具执行前安检，不通过就拦截，不关心是谁下的命令
- **上下文管理器** 默默监控 Token 消耗，超限了就触发截断
- **配置系统** 从不主动出现，需要参数时从它那里读取

这种设计叫做**关注点分离（Separation of Concerns）**。每个模块只做好一件事，模块之间通过明确定义的接口通信。这样，修改一个模块不会意外破坏另一个模块。

## 代码演示

```js
// 15 行代码的最小 Claude Code
// 把前 14 天的模块组装在一起
const { ToolRegistry, BashTool, WebFetchTool } = require("./tools");

class ClaudeCode {
  constructor(apiKey) {
    this.apiKey = apiKey;                          // Day 14: 配置
    this.registry = new ToolRegistry();            // Day 5: 工具注册表
    this.registry.register(new BashTool());       // Day 6: Bash 命令
    this.registry.register(new WebFetchTool());    // Day 9: 网络搜索
    this.history = [];                             // Day 8: 对话历史
  }

  // 核心循环：接收消息，返回回复
  async chat(message) {
    this.history.push({ role: "user", content: message });  // 记录用户消息

    // 调用 AI API（Day 4: 消息格式，Day 13: 错误处理）
    const response = await fetch("https://api.anthropic.com/v1/messages", {
      method: "POST",
      headers: {
        "x-api-key": this.apiKey,
        "anthropic-version": "2023-06-01",
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        model: "claude-sonnet-4-7-20250514",
        max_tokens: 4096,
        messages: this.history,
        // 把工具注册表转换成 AI 能理解的 schema（Day 5）
        tools: this.registry.list().map(t => t.toSchema()),
      }),
    });

    const data = await response.json();             // Day 13: 错误处理要加这里
    this.history.push({ role: "assistant", content: data.content[0].text });
    return data.content[0].text;
  }
}

console.log("你的 Claude Code 已经能跑了！");
console.log("前 14 天学的所有模块，现在组装成了一台能工作的机器。");
console.log("接下来：斜杠命令 → 任务拆解 → Plan 模式 → 上下文压缩...");
```

## 知识点速查表

| 架构原则 | 说明 |
|---------|------|
| 关注点分离 | 每个模块只做一件事，模块间通过接口通信 |
| 模块化设计 | 独立可测试，替换不影响整体 |
| 接口契约 | 模块之间用明确定义的数据格式通信 |
| 可组合性 | 简单模块组合成复杂系统 |
| 最小可行 | 先让它跑起来，再逐步增强 |

## 面试题

1. **如果让你把权限守卫从"可配置"改成"按目录差异化授权"，架构上需要改动多少？**需要改动权限守卫的核心 `check()` 方法。现有的 `Map<toolName, level>` 可以扩展为 `Map<pathPattern, level>` 或更复杂的 `PathPermissionResolver` 类。但接口不需要变（仍然是 `check(command, context)`），这正是关注点分离的好处——改动是局部的，不会在整个系统里扩散。

2. **架构中每个模块的错误处理策略是什么？**好的 Agent 架构需要分层错误处理：REPL 层捕获所有错误，给用户友好的提示，不让程序崩溃；QueryEngine 层捕获 AI 调用错误，触发重试（Day 13）；权限守卫层对危险命令直接拒绝并记录；工具执行层捕获命令执行错误，包含在工具响应里返回给 AI，让 AI 自己决定如何处理。不同层次的错误有不同的处理策略，不能一概而论。
