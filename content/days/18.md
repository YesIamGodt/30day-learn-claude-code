      ## PlanModeManager — 计划模式状态机

      Plan 模式是一种**安全机制**，它的核心思想是：在执行危险或有副作用的操作之前，先让 AI 描述它要做什么，用户确认后再行动。这就像航空管制——飞行员起飞前必须向塔台报告计划，塔台批准后才能执行。

      模式切换用 Enum 而非字符串常量（`Mode.NORMAL` vs `"normal"`）是关键设计。Enum 的好处是：
      1. **类型检查**：如果写错了，`Mode.UNKNOWN` 会在运行时或类型检查时报错，而 `"unknow"` 只是静默的拼写错误
      2. **IDE 自动补全**：输入 `Mode.` 时 IDE 会弹出所有选项
      3. **穷举检查**：用 `match/case` 时，如果加了新的模式，编译器会警告你漏掉了某个 case

      **`pending_plan` 的设计**是 Plan 模式的核心状态。在用户确认之前，计划内容存在 `pending_plan` 里；确认后复制到 `plan_history` 并清空 `pending_plan`（等待下次新计划）。这个分离保证了历史可追溯，同时状态不会混淆。

# Day 18: Plan 模式：AI 行动前先做计划

## 这一节要解决什么问题？

想象一下这个场景：用户让 AI "帮我删除所有日志文件"，AI 直接执行了 `rm -rf *.log`。结果用户其实想要的是"压缩"日志而不是删除。文件没了，用户欲哭无泪。

这类问题的根源是：**AI 和用户之间的意图对齐存在延迟**。AI 收到指令后立刻执行，中间没有确认环节。如果用户描述模糊或 AI 理解有误，错误执行的后果已经产生。

Plan 模式解决这个问题的思路是：**强制插入一个确认节点**。在 AI 执行任何操作之前：

1. AI 先描述计划（"我将删除所有 .log 文件，释放约 500MB 空间"）
2. 用户看到计划，决定是否批准
3. 批准后才真正执行

这个模式在很多场景下很有价值：删除操作、覆盖文件、修改系统配置、发送网络请求……任何"难以撤销"的操作都值得先过一遍 Plan 模式。

## Plan 模式状态机

```
用户输入大任务
      │
      ▼
┌─────────────────────────────────┐
│     PlanModeManager             │
│                                 │
│  [NORMAL] ──/plan──→ [PLAN]     │
│     ↑              │            │
│     └──/exit_plan──┘            │
└─────────────────────────────────┘
      │
 PLAN 模式下：
      │
      ▼
  生成计划 → 显示给用户
      │
      ├── 用户确认 → execute_if_normal() 放行
      └── 用户取消 → 清空 pending_plan，返回取消消息
```

## 概念图解

```
正常模式 vs Plan 模式执行流程对比

正常模式:
用户 → AI → 执行 [无确认]
                  ↓
            可能已造成不可逆后果

Plan 模式:
用户 → AI → 生成计划文本
              ↓
         显示计划给用户
              ↓
    ┌──────┴──────┐
    │ 确认        │ 取消
    ↓             ↓
执行计划      返回"已取消"
    ↓
✓ 操作成功，或错误处理
```

## 基础知识

### 模式切换

```js
class PlanMode {
```

模式切换命令可以集成到斜杠命令系统（Day 16）：`/plan` 进入计划模式，`/exit_plan` 退出计划模式。

## 进阶知识

### Python 实现中的模式枚举

```python
from enum import Enum

class Mode(Enum):
    NORMAL = "normal"   # 普通模式，直接执行
    PLAN = "plan"        # 计划模式，先计划后执行

class PlanModeManager:
    def __init__(self):
        self.mode = Mode.NORMAL
        self.plan_history: list[str] = []   # 已确认的历史计划
        self.pending_plan: str = ""          # 待确认的计划

    def is_plan_mode(self) -> bool:
        return self.mode == Mode.PLAN

    def enter_plan(self) -> str:
        self.mode = Mode.PLAN
        return "进入计划模式。请描述你想做什么，我会先给出计划，确认后才执行。"

    def approve_plan(self) -> str | None:
        """用户确认计划"""
        if not self.pending_plan:
            return None
        plan = self.pending_plan
        self.plan_history.append(plan)    # 存入历史
        self.pending_plan = ""            # 清空待确认
        self.mode = Mode.NORMAL           # 切回正常模式
        return plan
```

### 计划执行守卫

Python 中的 `execute_if_normal` 装饰了一个异步执行函数：

```python
async def execute_if_normal(self, action_fn):
    if self.is_plan_mode():
        return "[计划模式] 请先退出计划模式（/exit_plan）再执行。"
    return await action_fn()
```

这保证了一个原则：**计划模式下，普通执行请求会被拒绝**。用户必须先确认计划，才能执行具体操作。

## 代码演示

```js
// Plan 模式：在执行前先让 AI 生成计划，用户确认后再行动
class PlanMode {
  constructor(client) {
    this.client = client;
    this.enabled = false;   // 默认关闭
    this.planHistory = [];  // 历史计划记录
    this.pendingPlan = "";  // 待确认的计划
  }

  enable() { this.enabled = true; }
  disable() { this.enabled = false; }

  // 让 AI 生成结构化的执行计划
  async 生成计划(task) {
    const prompt = `任务：${task}
请分步骤说明你会怎么做。用以下格式：

## 计划
1. 第一步：...
2. 第二步：...
3. 第三步：...

## 预估影响
（简要说明每步的影响）
确认以上计划无误后，我会按顺序执行。`;

    const response = await this.client.messages.create({
      model: "claude-sonnet-4-7-20250514",
      max_tokens: 800,
      messages: [{ role: "user", content: prompt }],
    });

    return response.content[0].text;
  }

  // 带确认的执行：先计划，用户确认，再执行
  async 执行带确认(task, executor) {
    if (!this.enabled) {
      return await executor(task);  // 正常模式：直接执行
    }

    // Plan 模式：先生成计划
    const plan = await this.生成计划(task);
    this.pendingPlan = plan;

    console.log("\nAI 计划：");
    console.log(plan);
    console.log("\n按 Enter 确认执行，或输入 '取消' 终止：");

    // 简化演示：直接确认。真实场景用 readline 等待用户输入
    const confirmed = true;  // await waitForUserConfirmation();
    if (!confirmed) {
      this.pendingPlan = "";
      return { success: false, message: "用户取消" };
    }

    // 确认后：将待确认计划移入历史
    this.planHistory.push(this.pendingPlan);
    this.pendingPlan = "";
    return await executor(task);
  }
}

// 测试
const planMode = new PlanMode();
planMode.enable();
console.log("Plan 模式：", planMode.enabled ? "开启" : "关闭");

// 真实场景中，用户输入大任务时：
// 1. PlanMode.生成计划(task) → AI 返回分步计划
// 2. 显示计划，等待用户确认
// 3. 用户确认后，才调用 executor(task)
```

## 知识点速查表

| 概念 | 说明 |
|------|------|
| Plan 模式 | 执行前强制生成计划并等待用户确认 |
| Mode 枚举 | 用 Enum 而非字符串，避免拼写错误，支持 IDE 补全 |
| pending_plan | 待确认的计划，用户批准后移入 history |
| plan_history | 已确认执行过的计划，可追溯 |
| 意图对齐 | 让用户和 AI 在执行前就行动达成一致 |
| 执行守卫 | `execute_if_normal` 在 Plan 模式下拒绝普通执行请求 |

## 面试题

1. **Plan 模式和权限系统（Day 11）有什么区别？它们是互补还是重复的？**两者互补，但职责不同。权限系统是**机器层面的门卫**：它基于规则（危险命令模式）做判断，AI 无法绕过。Plan 模式是**人类层面的确认**：它不基于规则，而是让人类判断 AI 的计划是否正确。权限系统防的是"命令本身有危险"，Plan 模式防的是"AI 理解错了用户的意图"。一个危险的命令（比如删除日志文件）可能通过权限检查，但用户的意图可能是压缩而不是删除——Plan 模式就能抓住这个误执行。

2. **如何在 Plan 模式中加入"计划变更"能力？用户可以在确认前修改计划吗？**可以设计一个"计划编辑"机制：用户看到 AI 的计划后，可以输入修改意见（比如"把第一步改成先备份"），AI 收到后重新生成计划，再次展示给用户确认。这个循环可以重复，直到用户满意。实现方式是在 `pendingPlan` 字段外再加一个 `editing` 状态，或者把编辑意见追加到 `pendingPlan` 的修改轮次记录里。
