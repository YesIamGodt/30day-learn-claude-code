      ## ContextCompactor — 上下文压缩器

      ContextCompactor 解决的是**长对话的上下文膨胀问题**。随着对话进行，历史消息越来越多，很快就会触及上下文窗口上限（Day 12）。压缩器的任务是把"旧的、冗长的"历史变成"简洁的摘要"，腾出空间。

      **设计哲学：保守压缩**。Python 实现中，压缩后至少保留：

      - 最近 `max_messages // 2` 条消息（保持最近对话的完整性）

      这个策略叫做**首尾保留 + 中间摘要**，兼顾了：早期系统上下文（旧对话的开始意图）、最新活跃上下文（当前正在讨论的内容）、中间历史的浓缩信息（曾经讨论过但现在不重要的内容）。

      **`should_compact()` 和 `compact()` 分离**是良好的接口设计。`should_compact()` 判断"是否需要压缩"，返回布尔值；`compact()` 执行实际压缩操作。这种分离让调用方可以灵活决定何时检查（每次发消息前检查，或每 N 轮检查一次），而不是压缩器自己决定检查时机。

# Day 19: 历史压缩：太长了怎么办？

## 这一节要解决什么问题？

对话进行到第 30 轮时，历史消息已经占用了 150K tokens，只剩下 50K 的空间留给下一轮对话。再继续下去，Claude 就会开始"忘记"早期讨论的内容，甚至可能变得自相矛盾。

这时候我们需要**上下文压缩（Context Compaction）**：把冗长的历史变成简洁的摘要，释放上下文空间，同时尽量保留关键信息。

压缩和截断（Day 12）有什么区别？截断是简单删除旧消息，快但信息损失大；压缩是用 AI 把旧消息的内容提炼成摘要，信息密度更高，但速度慢且需要额外的 API 调用。两种方式各有适用场景，可以组合使用。

## 压缩策略对比

| 策略 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| 直接截断 | 删除最早的 N 条 | 简单、快速 | 可能丢失重要背景 |
| 首尾保留 | 保首尾，删中间 | 保留始末上下文 | 中间内容完全丢失 |
| 摘要压缩 | AI 生成摘要替换旧消息 | 保留关键信息 | 需要额外 API 调用 |
| 分层压缩 | 按重要度分级淘汰 | 最精细 | 实现最复杂 |

## 概念图解

```
压缩前（80 条消息，占用 160K tokens）:

[系统提示] [初始任务] [消息1] ... [消息78] [消息79]
 ↑
 太早了，可能已经不重要

压缩后（保留了精华）:

[系统提示] [初始任务] [摘要: 前78条消息的主要内容...] [消息78] [消息79]
  ↑              ↑                                      ↑
 永久保留      摘要替代旧历史                       最近的对话保留完整
```

## 基础知识

### Token 估算与压缩判断

```js
class ContextCompactor {
  constructor(maxTokens = 8000) {
    this.maxTokens = maxTokens;
  }

  // 估算 token 数（中英文混合公式）
  估算Token(text) {
    const 英文 = text.split(/\s+/).length;
    const 中文 = (text.match(/[\u4e00-\u9fa5]/g) || []).length;
    return Math.ceil(英文 * 1.3 + 中文);
  }

  // 判断历史是否需要压缩
  shouldCompact(messages) {
    const total = messages.reduce((sum, m) => sum + this.估算Token(m.content), 0);
    return total > this.maxTokens;
  }
}
```

### 摘要生成

**简单摘要**（不需要 AI 调用）：统计对话数量和主题关键词：

```js

  const userMsgs = messages.filter(m => m.role === "user");

AI 提供了 ${assistantMsgs.length} 个回复。
```

## 进阶知识

### Python 实现：首尾保留 + 中间摘要

```python
class ContextCompactor:
    def __init__(self, max_messages: int = 50, max_tokens: int = 8000):
        self.max_messages = max_messages      # 按消息条数判断
        self.max_tokens = max_tokens          # 按 token 数判断（可选）

    def should_compact(self, history: ConversationHistory) -> bool:
        return len(history.messages) > self.max_messages

    def compact(self, history: ConversationHistory, summary: str) -> None:
        keep = history.messages[:2]           # 永久保留前 2 条
        keep.append(Message(role="system", content=f"[历史摘要] {summary}"))
        keep.extend(history.messages[-self.max_messages // 2:])  # 保留最近一半
        history.messages.clear()
        history.messages.extend(keep)
```

### 压缩触发时机

压缩不应该太频繁（浪费资源），也不应该太晚（窗口已经满了）：

- **按消息数触发**：每 N 条消息检查一次，如 `len(messages) > max_messages`
- **按 Token 触发**：总 Token 数超过阈值时触发，更精确
- **按对话轮次触发**：每完成一轮对话检查一次（平衡精确度和性能）

## 代码演示

```js
// 上下文压缩器：把长对话历史压缩成简洁摘要
class ContextCompactor {
  constructor(maxTokens = 8000) {
    this.maxTokens = maxTokens;
  }

  // 估算 token 数（中英文混合）
  估算Token(text) {
    const 英文 = text.split(/\s+/).length;
    const 中文 = (text.match(/[\u4e00-\u9fa5]/g) || []).length;
    return Math.ceil(英文 * 1.3 + 中文);
  }

  // 策略一：直接截断，保留最新 N 条
  truncateToLimit(messages, maxMessages = 10) {
    const 系统 = messages.filter(m => m.role === "system");
    const 其他 = messages.filter(m => m.role !== "system");
    return [...系统, ...其他.slice(-maxMessages)];
  }

  // 策略二：生成摘要（不需要 AI API，用规则生成）
  summarize(messages) {
    const userMsgs = messages.filter(m => m.role === "user");
    const assistantMsgs = messages.filter(m => m.role === "assistant");

    const summary = `【对话摘要】
用户共发起 ${userMsgs.length} 个请求。
主要话题：${userMsgs[0]?.content.slice(0, 30) ?? "无"}...
AI 提供了 ${assistantMsgs.length} 个回复。
最后状态：${assistantMsgs[assistantMsgs.length - 1]?.content.slice(0, 30) ?? "无"}...`;
    return summary;
  }

  // 智能压缩入口：自动选择策略
  compress(messages) {
    let totalTokens = messages.reduce((sum, m) => sum + this.估算Token(m.content), 0);

    if (totalTokens <= this.maxTokens) {
      return messages;  // 还够用，不需要压缩
    }

    console.log(`⚠ 历史过长（${totalTokens} tokens），开始压缩...`);

    // 保留系统提示 + 生成摘要 + 最近 5 条
    const 系统 = messages.filter(m => m.role === "system");
    const 对话 = messages.filter(m => m.role !== "system");

    const summaryMsg = {
      role: "system",
      content: "【早期对话摘要】\n" + this.summarize(对话),
    };

    const 压缩后 = [summaryMsg, ...对话.slice(-5)];
    console.log(`✅ 压缩完成：${messages.length} 条 → ${压缩后.length} 条`);
    return [...系统, ...压缩后];
  }
}

// 测试：模拟 20 轮对话的压缩
const compactor = new ContextCompactor(2000);
const 长历史 = Array.from({ length: 20 }, (_, i) => ({
  role: i % 2 === 0 ? "user" : "assistant",
  content: `这是第 ${i + 1} 条消息，内容包含一些较长的对话记录供参考。`,
}));

const 压缩后 = compactor.compress(长历史);
console.log(`原始: ${长历史.length} 条, 压缩后: ${压缩后.length} 条`);
console.log("摘要内容示例:", 压缩后[0].content.slice(0, 100));
```

## 知识点速查表

| 概念 | 说明 |
|------|------|
| 上下文压缩 | 把冗长历史变成简洁摘要，释放 Token 空间 |
| 首尾保留 | 保留系统提示和最近消息，中间部分摘要替代 |
| 摘要生成 | 统计摘要（快但粗糙）或 AI 摘要（慢但精准） |
| should_compact | 判断"是否需要压缩"，返回布尔值 |
| 触发时机 | 按消息数、按 Token 数、按对话轮次 |
| 压缩不可逆 | 压缩会丢失细节，设计时要考虑是否可接受 |

## 面试题

1. **如果一段历史消息里包含"用户提供了数据库连接字符串"这样的敏感信息，压缩时应该如何处理？**敏感信息在摘要生成时必须被**识别并脱敏**，而不是直接放入摘要。有几种处理方式：1) 压缩前先扫描历史，用正则匹配敏感模式（密码、Key、连接字符串），用 `[REDACTED]` 替换；2) 把敏感信息移到单独的"安全存储"（不经过压缩器），压缩后仍然可以访问；3) 不压缩包含敏感信息的对话段落，直接删除。最安全的是方案 2，既不丢失信息，又不暴露在压缩摘要里。

2. **压缩后的摘要能否被"解压"恢复原始内容？为什么？**不能。摘要是一个有损压缩过程——它把 N 条消息压缩成 1 条摘要，原始信息已经丢失，无法逆向恢复。这和 ZIP 压缩（无损）不同，AI 摘要本质上是对话内容的"理解摘要"，不是"编码存储"。这也是为什么设计时需要在"压缩 aggressive"（丢弃更多细节）和"保留信息"之间做权衡。
