      ## retry — 指数退避重试装饰器

      网络请求永远不是 100% 可靠的。DNS 抖动、TCP 重传、服务器过载——这些临时性故障往往在几秒后自动恢复。重试机制就是利用这个特性，用时间换成功率。

      **指数退避（Exponential Backoff）** 的核心思想：每次失败后，等待时间翻倍。第一次失败等 1 秒，第二次等 2 秒，第三次等 4 秒……这样既不会对服务器造成额外压力，又能给故障足够的恢复时间。

      ```python
      delay = base_delay * (2 ** attempt)
      # attempt=0 → 1s, attempt=1 → 2s, attempt=2 → 4s
      ```

      **为什么是装饰器模式？** 因为重试逻辑是横切关注点（cross-cutting concern），它与业务逻辑正交。用装饰器包装，可以让任何函数瞬间获得重试能力，而不需要修改函数本身。

      **关键设计点**：
      - `max_attempts`：最多重试几次。第 1 次失败 + 2 次重试 = 共 3 次尝试。
      - `exceptions` 参数：只对指定异常类型重试，网络超时重试，程序逻辑错误不重试。
      - `@wraps(func)`：保留原函数的 `__name__`、`__doc__` 等元数据，对调试至关重要。

# Day 13: 错误处理：出错了怎么办？

## 这一节要解决什么问题？

写代码时，大多数人会先假设一切顺利：网络没问题、API 可用、文件存在。但现实是，这些假设几乎总是会在某个时刻被打破。

调用 AI API 会遇到什么问题？

- **网络抖动**：你的请求数据包在网络上丢了，TCP 重传需要时间
- **服务端过载**：API 服务器处理不过来，返回 429（Too Many Requests）
- **Key 无效或额度用完**：401 或 403 错误
- **临时性故障**：服务端某个组件抖动，几秒后自动恢复

如果每次 API 调用失败都直接抛异常给用户，用户体验会非常差。更合理的做法是：**分情况处理**。对于临时性故障，耐心等一下再试；对于永久性故障（如 Key 无效），立刻报错。

这就是错误处理 + 重试机制要解决的问题。

## 错误分类体系

```
可重试的错误（Transient Errors）
  ├── 网络超时（ECONNRESET、ETIMEDOUT）
  ├── 服务端过载（HTTP 429）
  └── 限流（Rate Limited）
  → 策略：指数退避重试

不可重试的错误（Permanent Errors）
  ├── 认证失败（HTTP 401、403）→ Key 问题
  ├── 权限不足（HTTP 403）→ 配置问题
  └── 业务错误（HTTP 400）→ 请求内容问题
  → 策略：立刻报错，给用户明确提示
```

## 概念图解

```
指数退避时间线（base_delay=1s, max_attempts=4）

尝试 1: ──[失败]──────────────────[等待 1s]──[失败]
                                              │
尝试 2: ───────────────────[等待 2s]────────[失败]
                                              │
尝试 3: ───────────────[等待 4s]─────────────[成功✓] 或 [失败]
                                              │
尝试 4: ───[等待 8s]────────────────────────[失败] → 最终抛异常

等待时间 = base_delay × 2^attempt
         = 1 × 2^0 = 1s
         = 1 × 2^1 = 2s
         = 1 × 2^2 = 4s
         = 1 × 2^3 = 8s（最大）
```

## 基础知识

### 错误分类与用户友好的提示

程序报错时，用户最关心的不是技术细节，而是"我该怎么办"。所以错误处理要转换视角——从"发生了什么"到"我应该做什么"：

```js
// 把技术错误翻译成用户友好的提示
function 翻译错误(error) {
  if (error.status === 401) {
    return "API Key 无效或已过期。请检查 ANTHROPIC_API_KEY 环境变量。";
  }
  if (error.status === 429) {
    return "请求频率超限。请等待几秒后再试，或设置更长的重试间隔。";
  }
  if (error.status === 400) {
    return "请求格式有问题（" + error.message + "）。请检查输入内容。";
  }
  return "发生未知错误：" + error.message;
}
```

### 可重试 vs 不可重试

判断一个错误是否值得重试，要考虑两个维度：**错误是否可能自行恢复**，以及**重试是否有代价**。

| 错误类型 | HTTP 状态码 | 典型原因 | 是否重试 |
|---------|-----------|---------|---------|
| 超时 | - | 网络抖动 | 是 |
| 连接重置 | - | TCP 不稳定 | 是 |
| 服务端过载 | 429 | 限流触发 | 是（带退避） |
| 认证失败 | 401 | Key 错误 | 否 |
| 权限不足 | 403 | 配置错误 | 否 |
| 参数错误 | 400 | 请求内容 | 否 |

## 进阶知识

### 装饰器模式实现重试

Python 实现中，重试逻辑用装饰器包装异步函数：

```python
def retry(max_attempts: int = 3, base_delay: float = 1.0,
          exceptions: Tuple[Type[Exception], ...] = (Exception,)):
    def decorator(func):
        @wraps(func)  # 保留原函数的元数据（__name__、__doc__）
        async def wrapper(*args, **kwargs):
            for attempt in range(max_attempts):
                try:
                    return await func(*args, **kwargs)  # 成功就直接返回
                except exceptions as e:
                    if attempt == max_attempts - 1:
                        raise  # 最后一次也失败，向上抛出
                    delay = base_delay * (2 ** attempt)  # 指数退避
                    logger.warning(f"{func.__name__} 失败，{delay:.1f}s 后重试: {e}")
                    await asyncio.sleep(delay)  # 异步等待，不阻塞事件循环
        return wrapper
    return decorator
```

`@wraps(func)` 非常重要——没有它，`func.__name__` 会变成 `"wrapper"`，调试时看到一堆错误都指向 `"wrapper"` 会很头疼。

### 带抖动的退避（Jittered Backoff）

纯指数退避在多个客户端同时重试时，会造成**惊群效应（Thundering Herd）**——大量客户端在同一时刻一起重试，把服务器再次冲垮。

解决方案是加随机抖动：

```python
import random

def jittered_delay(attempt, base_delay=1.0, jitter=0.5):
    """在指数退避基础上加 ±50% 随机抖动"""
    exp_delay = base_delay * (2 ** attempt)
    # jitter=0.5 表示在 [50%, 150%] 范围内随机
    return exp_delay * (1 + random.uniform(-jitter, jitter))
```

## 代码演示

```js
// 重试装饰器工厂：返回一个新的带重试能力的函数
async function withRetry(fn, maxRetries = 3, delayMs = 1000) {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await fn();  // 成功直接返回
    } catch (error) {
      // 判断是否可重试：检查错误码
      const isRetryable = ["ECONNRESET", "ETIMEDOUT", "429"].some(
        code => error.message.includes(code)
      );

      if (!isRetryable || attempt === maxRetries) {
        throw error;  // 不可重试的错误直接抛出
      }

      // 指数退避：每次失败等待时间翻倍
      const delay = delayMs * attempt;
      console.log(`⚠ 第 ${attempt} 次失败: ${error.message}`);
      console.log(`   ${delay}ms 后重试...`);
      await new Promise(r => setTimeout(r, delay));  // 异步等待
    }
  }
}

// API 错误类：区分不同类型的错误
class APIError extends Error {
  constructor(message, code, status) {
    super(message);
    this.code = code;    // 错误码（如 "invalid_api_key"）
    this.status = status;  // HTTP 状态码
  }
}

// 带重试的 AI 调用
async function 安全调用AI(messages, model) {
  try {
    const response = await withRetry(async () => {
      const res = await fetch("https://api.anthropic.com/v1/messages", {
        method: "POST",
        headers: {
          "x-api-key": process.env.ANTHROPIC_API_KEY,
          "anthropic-version": "2023-06-01",
          "Content-Type": "application/json",
        },
        body: JSON.stringify({ model, messages, max_tokens: 1024 }),
      });

      if (!res.ok) {
        const body = await res.json().catch(() => ({}));
        throw new APIError(
          body.error?.message ?? `HTTP ${res.status}`,
          body.error?.type ?? "unknown",
          res.status
        );
      }

      return res.json();
    });

    return response;
  } catch (e) {
    // 将技术错误转换为用户友好的提示
    if (e instanceof APIError) {
      if (e.status === 401) throw new Error("API Key 无效，请检查 ANTHROPIC_API_KEY");
      if (e.status === 429) throw new Error("请求频率超限，请稍后再试");
      throw new Error(`AI 调用失败: ${e.message}`);
    }
    throw new Error(`未知错误: ${e.message}`);
  }
}

// 测试
console.log("错误处理演示：无 API 调用，仅展示架构");
console.log("真实场景中，429 会被指数退避重试，401 会立刻报错");
```

## 知识点速查表

| 概念 | 说明 |
|------|------|
| 指数退避 | 每次失败等待时间翻倍：1s → 2s → 4s → 8s |
| 装饰器模式 | 横切关注点包装，不修改原函数即可添加重试能力 |
| @wraps | Python 装饰器保留原函数元数据，对调试至关重要 |
| 可重试错误 | 临时性故障（超时、限流），带退避重试 |
| 不可重试错误 | 永久性故障（认证失败），立刻报错 |
| 抖动（Jitter） | 在退避时间上加随机偏移，避免惊群效应 |
| 异步 sleep | `asyncio.sleep()` 不阻塞事件循环，允许并发其他任务 |

## 面试题

1. **重试次数设置为多少合适？为什么不是无限重试？**重试次数与错误类型相关：网络超时建议 3-5 次（大多数临时故障在 10s 内恢复），API 限流建议 3-5 次（带更长退避）。无限重试的问题是：如果错误是永久性的（Key 无效），无限重试会让程序永远卡住，用户无法得到反馈。此外，重试本身有代价（时间、资源），代价超过收益时就不该重试。

2. **如何设计一个"熔断器（Circuit Breaker）"来防止重试风暴？**熔断器的核心思想是：当错误率超过阈值时，"熔断"——在一段时间内不再尝试，直接快速失败。三个状态：Closed（正常，重试可用）、Open（熔断，直接拒绝）、Half-Open（尝试一个请求，探测是否恢复）。Python 实现可以用计数器跟踪连续失败次数，超过阈值切换到 Open 状态。
