# Day 1: 命令行入口

## 这一节要解决什么问题？

我们每天用电脑，点来点去是**图形界面**（GUI）。鼠标点击图标、拖动窗口——这些操作直观友好，但缺点是**难以自动化**。程序员需要的是：能不能用文字命令让电脑自动干活？于是有了**命令行界面**（CLI）。只有文字，键盘输入，不需要鼠标，输出结果直接打印在终端上。

Claude Code 本身就是一个命令行工具。当你运行 `claude` 或者 `node index.js "帮我写代码"` 时，实际上是在告诉操作系统："启动这个程序，把这串文字传给它"。操作系统通过 `process.argv` 把用户的原始输入打包成字符串数组，交给程序处理。这就是整个 CLI 的起点——理解这一步，才能理解 Agent 是怎么"接收指令"的。

传统 GUI 程序和 CLI 程序的区别，本质上是**人机交互范式**的不同。GUI 靠事件驱动（点击了哪个按钮？），CLI 靠参数驱动（收到了什么字符串？）。对于构建 AI Agent 来说，CLI 更适合，因为 AI 的输入本来就是自然语言，我们只需要把这段文字交给 Agent 核心模块处理即可。

## 概念图解

```
+----------------------------------------------------------+
|                    命令行调用全过程                        |
+----------------------------------------------------------+

用户输入（终端）:
  $ node index.js "帮我写排序算法" --verbose --model sonnet

                                    ↓
              process.argv 数组（Node.js 提供）:
  ["node", "index.js", "帮我写排序算法", "--verbose", "--model", "sonnet"]
   argv[0]  argv[1]   argv[2]           argv[3]      argv[4]   argv[5]
   (程序名)  (脚本名)   (用户指令)         (flag)       (flag)   (flag值)

                                    ↓
              CLI 解析器做两件事:
              1. 分离位置参数（用户指令）→ 传给 AI 核心
              2. 分离 flags（--verbose）→ 控制程序行为

                                    ↓
              最终得到:
              prompt = "帮我写排序算法"
              flags  = { verbose: true, model: "sonnet" }
```

## 基础知识

### 1. process.argv 详解

`process.argv` 是 Node.js 内置的全局数组，包含了启动进程时的完整命令行参数。`argv[0]` 是 Node.js 可执行文件的绝对路径，`argv[1]` 是脚本文件的绝对路径，从 `argv[2]` 开始才是真正的用户参数。

```js
// 在终端运行: node index.js "你好" --verbose
// process.argv 的实际内容：
console.log(process.argv);
// [
//   '/usr/local/bin/node',   // argv[0] — Node 路径
//   '/path/to/index.js',     // argv[1] — 脚本路径
//   '你好',                   // argv[2] — 用户指令
//   '--verbose'              // argv[3] — flag
// ]

// 去掉前两项，剩下的才是我们关心的参数
const args = process.argv.slice(2);
console.log(args); // [ '你好', '--verbose' ]
```

### 2. 位置参数 vs Flags

命令行参数分为两类：**位置参数**（Positional Arguments）和**Flags**（可选开关）。位置参数的含义由顺序决定，`--verbose` 这类 flag 则以双横线开头，含义由名称决定，与顺序无关。

```js
// 解析逻辑：遍历数组，-- 开头的是 flag，否则是位置参数
const args = ["帮我写排序", "--verbose", "--model", "sonnet"];

const positionals = [];   // 位置参数
const flags = {};          // flag 字典

for (let i = 0; i < args.length; i++) {
  const arg = args[i];
  if (arg.startsWith("--")) {
    // 检查下一个参数是否是 flag 的值（不以 -- 开头）
    const key = arg.slice(2);            // 去掉 --
    const next = args[i + 1];
    if (next && !next.startsWith("--")) {
      flags[key] = next;                  // --model sonnet  →  flags.model = "sonnet"
      i++;                                // 跳过下一个，因为已经处理过了
    } else {
      flags[key] = true;                  // --verbose（无值）→  flags.verbose = true
    }
  } else {
    positionals.push(arg);                // 普通参数推进位置参数数组
  }
}

console.log(positionals); // [ '帮我写排序' ]
console.log(flags);       // { verbose: true, model: 'sonnet' }
```

### 3. 真实项目的 CLI 入口

在 Claude Code 的 Python 版本中，`__main__.py` 或 `cli.py` 文件负责解析命令行参数，将用户指令交给 Agent 核心模块。这个模式在所有 CLI 工具中通用——无论是 `git commit -m "fix bug"` 还是 `docker run -it ubuntu bash`，核心逻辑都是：接收参数 → 解析 → 分发给对应模块。

## 进阶知识

### 环境变量与秘密管理

CLI 程序除了接收命令行参数，另一个重要信息入口是**环境变量**。API Key 这类敏感信息绝不能写在命令行里（会暴露在进程列表中），而应该通过环境变量传入：

```bash
# 错误：API Key 会出现在 ps aux 等命令的输出中
$ node index.js "做某事" --api-key sk-123456

# 正确：环境变量对进程私有
$ ANTHROPIC_API_KEY=sk-123456 node index.js "做某事"
```

在代码中，用 `process.env.ANTHROPIC_API_KEY` 读取，环境变量不存在时返回 `undefined`，可以用 `||` 提供默认值。

### 跨平台路径处理

Windows 使用反斜杠 `\` 作为路径分隔符，而 macOS 和 Linux 使用正斜杠 `/`。Node.js 的 `path` 模块提供了 `path.join()` 自动处理这个差异——始终用 `/` 书写路径，让 `path.join` 负责转换成当前系统的格式：

```js
const path = require("path");
// 在任何系统上都能正确工作
const configPath = path.join(__dirname, "..", "config", "settings.json");
```

## 代码演示

下面这段代码演示了 CLI 参数解析的完整逻辑。为了让浏览器里也能直接跑，我用硬编码的示例参数来演示：

```js
// === 在真实 Claude Code 项目中，args 来自 process.argv ===
// === 这里用硬编码演示，实际项目里会从命令行读取 ===

const args = ["帮我写排序算法", "--verbose"]; // 模拟 process.argv.slice(2)

// 核心逻辑：把 -- 开头的参数挑出来
const flags = args.filter(a => a.startsWith("--"));
const rest = args.filter(a => !a.startsWith("--"));

console.log("=== CLI 参数解析演示 ===");
console.log("原始参数数组:", args);
console.log("位置参数（真实指令）:", rest.join(" "));
console.log("Flags（可选开关）:", flags);
console.log("");

if (flags.includes("--verbose")) {
  console.log("详细信息已开启：");
  console.log("  - 将执行任务:", rest[0]);
  console.log("  - 附加标志:", flags.join(", "));
}
```

运行效果（上面代码的输出）：

```
=== CLI 参数解析演示 ===
原始参数数组: [ '帮我写排序算法', '--verbose' ]
位置参数（真实指令）: 帮我写排序算法
Flags（可选开关）: [ '--verbose' ]

详细信息已开启：
  - 将执行任务: 帮我写排序算法
  - 附加标志: --verbose
```

## 知识点速查表

| 概念 | 说明 | 示例 |
|------|------|------|
| `process.argv` | Node.js 全局数组，包含所有命令行参数 | `argv[2]` = 第一个用户参数 |
| 位置参数 | 无前缀，靠顺序决定含义的参数 | `"帮我写代码"` |
| Flag（可选参数） | 以 `--` 开头的可选开关 | `--verbose`, `--model sonnet` |
| `slice(2)` | 去掉 `node` 和 `脚本名`，只留用户参数 | `process.argv.slice(2)` |
| `process.env` | 读取环境变量，安全存储 API Key | `process.env.ANTHROPIC_API_KEY` |
| `path.join()` | 跨平台路径拼接，自动处理 `/` vs `\` | `path.join(__dirname, "config")` |

## 面试题

**Q1: 如果用户同时输入了 `--verbose` 和 `--quiet` 两个互斥的 flag，你的解析代码应该怎么处理？**

提示：从用户体验角度思考，不仅仅是"以最后一个为准"这么简单。合理的做法可能是：解析时检查冲突，给出警告或报错，而不是默默忽略其中一个。

**Q2: `process.argv` 和环境变量 `process.env` 在安全上有何区别？分别在什么场景下使用？**

提示：考虑进程信息的可见性（`ps` 命令、`/proc` 文件系统），以及不同平台的差异。
